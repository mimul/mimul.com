프리미티브 타입으로 도메인 개념을 표현하다 보면 흔히 부딪히는 문제가 있다.

```java
void createUser(String email, int age, String postalCode) { ... }
```

이 시그니처만 보고는 `email`이 올바른 형식인지, `age`가 음수가 아닌지, `postalCode`가 특정 형식을 따르는지 알 방법이 없다. 검증 로직은 메서드 본문에 흩어지고, 같은 검사가 여러 곳에 중복된다. Value Object는 이 문제를 타입 수준에서 해결한다. 이 글은 도메인 모델을 Java로 작성하는 개발자를 대상으로, Value Object가 무엇인지, 엔티티와 어떻게 다른지, 왜 생성자에서 검증해야 하는지, 언제 도입하고 어디서 멈추는지, 그 검증을 어디에 두는지를 순서대로 정리한다.

## Value Object란

Martin Fowler는 Value Object를 보유한 속성의 값 때문에 같다고 판정되는 객체라고 정의한다. 메모리 주소나 식별자가 아닌, 객체가 보유한 값 자체로 같은지를 판단한다. 예를 들어 2D 좌표 `(1, 2)`와 `(1, 2)`는 서로 다른 인스턴스라도 같다고 봐야 한다. 반면 두 명의 직원은 이름이 같더라도 사번이 다르면 다른 사람이다. 전자가 Value Object의 사고방식이고, 후자는 엔티티의 사고방식이다. Fowler는 좌표, 금액, 범위처럼 작은 객체를 대표적인 예로 들면서도, 개념적 정체성이 없고 참조를 공유할 이유가 없다면 더 큰 구조도 Value Object로 만들 수 있다고 덧붙인다.

Eric Evans는 같은 것을 도메인 쪽에서 본다. Value Object는 개념적 정체성 없이 도메인의 어떤 측면을 서술하는 객체이고, 무엇인가를 고유하게 식별해 변경을 추적할 필요가 없을 때 쓴다. 금액처럼 필드가 하나인 것도, 날짜 범위나 주소처럼 필드가 여럿인 것도 Value Object가 된다.

용어 혼동도 주의할 필요가 있다. 2000년대 초 J2EE 문헌에서는 "Value Object"를 Data Transfer Object(DTO)의 뜻으로 쓴 사례가 많았다. 지금도 Value Object를 "DB에서 조회한 데이터를 담는 객체"로 이해하는 경우가 있는데, 이는 DDD에서 말하는 Value Object와 다른 개념이다. DDD의 Value Object는 전송 컨테이너가 아니라 도메인 개념을 값으로 표현하는 객체다.

## 엔티티와 Value Object의 차이

| | 엔티티 | Value Object |
|---|---|---|
| **동등성 판정** | 식별자가 같으면 동일 | 보유한 속성이 모두 같으면 동일 |
| **가변성** | 시간에 따라 속성 변경 가능 | 원칙적으로 불변 |
| **수명** | 생성부터 소멸까지 연속된 이력을 가짐 | 수명이라는 개념이 없음 |

직원 "김철수"는 부서가 바뀌고 나이가 들어도 같은 직원이다(엔티티). 반면 100원짜리 동전은 어느 동전이냐가 아니라 그 가치가 중요하다. 어느 100원이든 같다(Value Object).

불변성의 차이도 직관적으로 이해할 수 있다. 100원짜리 동전에 새겨진 "100"이라는 숫자를 지우고 "500"으로 고치지 않는다. 100원을 500원으로 바꾸고 싶다면, 100원짜리를 버리고 500원짜리를 새로 꺼낸다. Value Object의 값이 바뀔 때는 객체를 수정하는 것이 아니라 새로운 객체로 교체한다.

수명의 차이는 식별자의 유무에서 따라 나온다. 엔티티는 식별자로 "그 직원"을 계속 가리킬 수 있으므로 생성부터 소멸까지 연속된 이력을 갖고, 그 변화의 역사(부서 이동, 승진)가 추적 대상이 된다. 반면 Value Object는 같은 값을 가진 두 인스턴스를 구별할 수 없으므로, 이 객체가 언제 생겨 언제 사라졌는지를 물을 대상 자체가 없다. 필요할 때 만들고, 쓰고, 버려도 도메인에는 아무 일도 일어나지 않는다.

엔티티와 Value Object는 대립 관계가 아니다. Value Object는 수명이 없으므로 저장될 때는 항상 어느 엔티티에 속하고, Value Object를 위한 테이블을 따로 두지 않고 부모 엔티티의 테이블에 함께 넣는 것이 보통이다. `User` 엔티티가 `Email`, `Age`, `PostalCode`라는 Value Object를 속성으로 갖는 식이다.

Value Object가 엔티티를 가리킬 수도 있다. 주문 항목이라는 Value Object가 상품 엔티티를 가리키는 식이다. 다만 애그리거트(함께 저장되고 함께 규칙을 지키는 객체 묶음)의 경계를 넘을 때는 `Product` 객체를 통째로 들고 있는 대신 `ProductId`처럼 식별자 하나만 감싼 Value Object로 참조한다. DDD의 애그리거트 규칙은 외부에서 애그리거트의 루트만 참조하라고 하고, 이를 한 걸음 더 밀면 다른 애그리거트는 객체가 아니라 식별자로만 참조하라는 규칙이 된다. 식별자로만 연결되므로 두 애그리거트 사이의 결합이 느슨해지고, 주문을 읽을 때 상품까지 딸려 오지 않는다.

반대로 Value Object끼리의 양방향 참조는 만들지 않는다. 불변 객체 둘이 서로를 품으려면 각각 생성 시점에 상대를 받아야 하므로 애초에 만들 수 없고, 가변으로 억지로 만들더라도 값으로 같은지 비교하는 `equals()`가 서로를 끝없이 호출한다. 주소가 우편번호를 품는 것처럼 한 방향으로 포함하는 구조면 충분하다.

어떤 개념이 Value Object인지 엔티티인지는 고정되지 않는다. 우편주소를 예로 들면, 쇼핑몰에서 "배송지 주소"는 값만 같으면 동일하게 취급되므로 Value Object가 자연스럽다. 하지만 부동산 관리 시스템에서 주소는 각 건물을 고유하게 식별하는 기준이 되므로 엔티티가 더 적합하다. 같은 개념이라도 도메인의 맥락과 모델링 목적에 따라 Value Object가 되기도 하고 엔티티가 되기도 한다.

판단이 어려울 때는 그 개념을 정수로 바꿔 놓고 생각해 보는 방법이 쓸 만하다. 정수 5를 쓸 때 "어느 5인지"는 아무도 신경 쓰지 않는다. 어떤 개념이 이처럼 값만 중요하고 어느 인스턴스인지가 중요하지 않다면 Value Object로 모델링하는 것이 자연스럽다.

## Value Object의 특성

### 불변성

Value Object는 생성 후 상태가 변하지 않는다. Java에서는 setter를 제공하지 않고 필드를 `final`로 선언하는 방식으로 구현한다.

```java
final class Money {
    private final int amount;
    private final Currency currency;

    public Money(int amount, Currency currency) {
        if (amount < 0) throw new IllegalArgumentException("금액은 0 이상이어야 합니다.");
        this.amount = amount;
        this.currency = currency;
    }

    public Money add(Money other) {
        if (!this.currency.equals(other.currency)) {
            throw new IllegalArgumentException("통화가 일치하지 않습니다.");
        }
        return new Money(this.amount + other.amount, this.currency);
    }

    // equals()와 hashCode()는 다음 절의 PostalCode와 같은 방식이므로 생략
}
```

`add()` 메서드는 기존 객체를 수정하지 않고 새로운 `Money` 객체를 반환한다. 불변이어야 하는 이유는 두 가지다. 첫 번째는 **별명 참조 문제(aliasing bug)** 다. Fowler가 든 예시가 직관적이다.

```java
Date partyDate = retirementDate;
partyDate.setDate(5);   // retirementDate도 함께 바뀐다
```

두 변수가 동일한 객체를 가리키므로, 한쪽을 수정하면 다른 쪽도 예상치 못하게 바뀐다. 두 번째는 해시 기반 컬렉션이다. Value Object는 다음 절에서 보듯 `hashCode()`를 값으로 계산하는데, `HashMap`의 키로 넣은 뒤 값이 바뀌면 해시가 달라져 넣은 항목을 다시 찾지 못한다. Value Object를 불변으로 만들면 참조를 몇 개나 공유하든, 어느 컬렉션에 넣든 이 두 문제가 생기지 않는다. 그래서 객체를 캐싱하거나 여러 스레드에서 공유해도 동기화 없이 안전하다.

불변이 원칙이지만 Evans는 예외를 둔다. 값이 매우 자주 바뀌고, 객체 생성과 폐기 비용이 크며, 교체가 메모리나 저장소의 군집을 흐트러뜨리는 경우에 한해 가변 Value Object를 허용한다. 그때도 조건이 하나 붙는다. 가변 Value Object는 공유하지 않는다. 공유된 가변 Value Object는 곧 별명 참조 문제의 근원이 되기 때문이다. 이 예외에 해당하지 않는데 불변으로 만들 수 없다면, 그 개념은 Value Object가 아니라고 보는 편이 안전하다.

### 값 동등성

두 Value Object는 보유한 값이 같으면 동일하다. Java에서는 `equals()`와 `hashCode()`를 재정의해서 이를 구현한다.

```java
final class PostalCode {
    private final String code;

    private PostalCode(String code) {
        this.code = code;
    }

    public static PostalCode of(String code) {
        if (!code.matches("\\d{5}")) {
            throw new IllegalArgumentException("올바르지 않은 우편번호 형식입니다.");
        }
        return new PostalCode(code);
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof PostalCode)) return false;
        return code.equals(((PostalCode) o).code);
    }

    @Override
    public int hashCode() {
        return code.hashCode();
    }
}
```

`equals()`가 식별자 대신 값을 비교하므로, 서로 다른 경로로 만들어진 두 `PostalCode`도 코드가 같으면 같은 우편번호다. 생성자를 숨기고 `of`라는 정적 메서드로만 만들게 한 이유는 "생성 시점에 검증을 모으기" 절에서 다룬다.

### 도메인 로직의 응집

Value Object는 단순히 값을 담는 그릇이 아니다. 그 값과 관련된 도메인 로직도 함께 가질 수 있다.

```java
final class Age {
    private final int value;

    private Age(int value) {
        this.value = value;
    }

    public static Age of(int value) {
        if (value < 0 || value > 150) throw new IllegalArgumentException("올바르지 않은 나이입니다.");
        return new Age(value);
    }

    public boolean isAdult() {
        return value >= 19;
    }
}
```

이메일 형식 검증을 `User` 엔티티에 두는 것보다 `Email` Value Object에 두는 편이 응집도가 높다. 나이의 성인 판정 로직이 `User`에 있는 것보다 `Age`에 있는 것이 더 자연스럽다. 관련 있는 것끼리 묶이므로 관련 없는 곳에서 동일한 로직이 중복될 가능성이 줄어든다.

나이는 단순한 정수가 아니다. 정수에 허용되는 연산이라도 나이에 곱셈이나 나눗셈을 적용하는 것은 도메인적으로 무의미하기 때문이다. 전용 타입으로 묶으면 이런 부적절한 연산이 자연스럽게 차단된다.

## 생성 시점에 검증을 모으기

### 부분함수와 Parse, don't validate

Value Object의 생성자에서 검증을 수행하는 것은 단순한 방어 코딩이 아니라 "Parse, don't validate"(검증하지 말고 파싱하라)라는 원칙의 적용이다.

이 원칙의 출발점은 **부분함수(partial function)** 문제다. 부분함수는 일부 입력에 대해서는 결과를 내지 못하는 함수를 말한다. 리스트의 첫 번째 원소를 꺼내는 함수가 대표적이다. 빈 리스트가 들어오면 돌려줄 원소가 없다. 이를 모든 입력에 대해 동작하게 만드는 방법은 두 가지다. 반환 타입을 `Optional`로 약화해 빈 경우를 호출자에게 떠넘기거나, 인자 타입을 "비어있지 않은 리스트"로 강화해 빈 경우가 들어오지 못하게 하는 것이다.

첫 번째 길을 택하면 이미 확인한 사실이 타입에서 사라진다.

```java
List<String> configDirs = getConfigurationDirectories(); // 내부에서 비어있지 않음을 이미 검증함
Optional<String> first = configDirs.stream().findFirst();
if (first.isPresent()) {
    initializeCache(first.get());
} else {
    throw new RuntimeException("should never happen"); // 중복 검증
}
```

`getConfigurationDirectories()`에서 이미 비어있지 않음을 확인했지만, 반환 타입이 평범한 `List`이므로 호출 지점에서 또 확인해야 한다. `"should never happen"` 주석이 달린 예외 처리는 이 패턴의 전형적인 신호다. 한 곳에서 확인한 사실을 타입 시스템이 기억하지 못하기 때문에 발생하는 중복이고, 누군가 안쪽의 검사를 지우더라도 이 코드는 그대로 컴파일되므로 컴파일러는 둘 사이의 의존을 알지 못한다.

두 번째 길은 더 구체적인 타입으로 파싱해 인자 타입을 강화하는 것이다. "비어있지 않은 리스트"를 별도의 타입으로 표현하면, 검증을 통과한 사실이 타입에 기록되고 이후 코드는 그 사실을 타입만으로 신뢰할 수 있다. 이것이 파싱이다. 검증은 입력을 확인만 하고 그 결과를 버리지만, 파싱은 확인한 결과를 새 타입으로 돌려준다.

검증만 하고 타입을 바꾸지 않으면, 검증 로직이 호출 지점마다 흩어지는 "Shotgun Parsing" 안티패턴이 된다. 입력의 일부가 유효함을 확인하고 처리를 시작한 뒤 다른 부분에서 무효함을 발견하는 상황이 생기고, 그 시점에는 잘못된 입력의 일부가 이미 처리된 뒤라 되돌리기 어렵다.

실무에서 전환 지점을 찾는 단서는 `void`를 반환하는 검증 메서드다. `void validateEmail(String email)` 형태는 검증 결과를 버린다. 반환값이 없으면 그 지식이 타입 시스템에 기록되지 않고, 호출자가 동일한 검증을 반복할 가능성이 남는다. `Email parseEmail(String email)`처럼 더 구체적인 타입을 반환하도록 바꾸면 그 지식이 보존된다.

### Smart Constructor

이 원칙을 Java의 Value Object에 적용한 패턴이 **Smart Constructor** 다. 생성자를 `private`으로 막고, 검증 로직을 포함한 정적 팩토리 메서드를 통해서만 객체를 만들 수 있게 한다.

```java
final class Email {
    private final String value;

    private Email(String value) {  // 직접 생성 불가
        this.value = value;
    }

    public static Email of(String raw) {  // Smart Constructor
        if (!raw.contains("@")) throw new IllegalArgumentException("올바르지 않은 이메일 형식입니다.");
        return new Email(raw);
    }
}

void createUser(Email email) {
    sendWelcomeEmail(email); // 이미 유효하다는 것이 타입으로 보장됨
}
```

앞의 `Money`처럼 public 생성자로도 검증은 가능하다. Smart Constructor의 차이는 "검증을 거치지 않고는 이 객체를 만들 수 없다"는 것을 구조적으로 강제한다는 점이다. 호출자가 실수로 `new Email("invalid")`처럼 검증 경로를 우회할 여지 자체를 없앤다. `Email` 타입을 받는 메서드는 검증을 다시 할 필요가 없다. 타입 자체가 "이미 검증된 이메일"임을 보장하기 때문이다.

이 패턴은 두 부분으로 이루어진다. 하나는 원시값을 감싸 컴파일러가 구별할 수 있는 별도 타입을 만드는 것이고, 다른 하나는 그 타입의 생성 경로를 검증을 거치는 하나로 좁히는 것이다. 감싸는 쪽을 TypeScript 진영에서는 브랜드 타입(branded type), Haskell에서는 newtype이라 부른다. 감싸기만 해서는 표식이 붙었다는 사실밖에 보장하지 못하고, 생성자를 숨기고 검증하는 팩토리만 열어 두어야 그 표식이 "검증을 통과했다"는 뜻이 된다.

### 필드 사이의 관계까지 타입에 싣기

앞의 `Email`과 `Age`는 값 하나의 형식을 검증했다. 같은 방식은 필드 여러 개에 걸친 규칙에도 쓸 수 있다.

```java
// 잘못된 상태가 표현 가능한 구조
class DateRange {
    public LocalDate start;  // null 가능
    public LocalDate end;    // null 가능, start 이전일 수도 있음
}

// 잘못된 인스턴스가 존재할 수 없게 만든 구조
final class DateRange {
    private final LocalDate start;
    private final LocalDate end;

    private DateRange(LocalDate start, LocalDate end) {
        this.start = start;
        this.end = end;
    }

    public static DateRange of(LocalDate start, LocalDate end) {
        Objects.requireNonNull(start, "시작일은 null일 수 없습니다.");
        Objects.requireNonNull(end, "종료일은 null일 수 없습니다.");
        if (!end.isAfter(start)) throw new IllegalArgumentException("종료일은 시작일 이후여야 합니다.");
        return new DateRange(start, end);
    }
}
```

`DateRange` 인스턴스가 존재한다는 사실 자체가 "start < end이고, 둘 다 null이 아니다"를 보장한다. 값 하나의 형식이든 필드 사이의 관계든, 불변식을 생성 시점에 한 번 확인하고 그 뒤로는 타입이 기억하게 한다는 점은 같다.

이 방식과 자주 함께 언급되는 원칙이 "Make Illegal States Unrepresentable"(불가능한 상태를 표현할 수 없게 만들기)이다. 둘은 겹치지만 같지 않다. `DateRange.of`는 잘못된 조합을 런타임에 거부할 뿐, 잘못된 조합을 적어 보는 것까지 막지는 못한다. 이 원칙이 말하는 것은 한 단계 위다. 잘못된 상태를 적을 자리 자체가 타입에 없도록 자료구조를 고르는 것이다. 결제 여부를 `boolean paid`와 null이 될 수 있는 `LocalDate paidAt` 두 필드로 두면 "결제했는데 날짜가 없음"과 "결제하지 않았는데 날짜가 있음"이 적힐 수 있다. 결제 전과 결제 후를 별개의 타입으로 나누고 날짜는 결제 후 타입에만 두면 그 두 조합은 적을 수조차 없다.

```java
abstract class PaymentStatus {}

final class Unpaid extends PaymentStatus {}

final class Paid extends PaymentStatus {
    private final LocalDate paidAt;   // 결제 후에만 존재하는 필드

    Paid(LocalDate paidAt) {
        this.paidAt = Objects.requireNonNull(paidAt);
    }
}
```

Parse, don't validate를 쓴 글도 이 순서를 권한다. 먼저 자료구조로 막고, 종료일이 시작일 뒤여야 한다는 순서 관계처럼 타입으로 표현하기 어려운 규칙에만 Smart Constructor로 검증기를 파서처럼 쓴다. `DateRange`는 후자의 자리에 있다.

## 두 방향의 안티패턴

**Primitive Obsession** 은 실제로 복잡한 개념을 프리미티브 타입으로만 다루는 문제다. 겉으로는 단순해 보이지만, 코드가 쌓이면 세 가지 증상이 나타난다.

```java
// 인자 순서를 바꿔도 컴파일러가 잡지 못한다
void register(String email, String postalCode) { ... }
register(postalCode, email); // 런타임에야 버그 발견
```

- **타입이 의미를 잃는다**: `String` 파라미터가 이메일인지, 계좌 ID인지, 우편번호인지 시그니처만 봐서는 알 수 없다.
- **검증이 중복된다**: 같은 이메일 형식 검사가 컨트롤러, 서비스, 리포지토리에 각각 흩어진다.
- **잘못된 결합이 허용된다**: 위 코드처럼 인자 순서가 바뀌어도 컴파일러가 잡지 못한다.

`Email`과 `PostalCode` 타입을 도입하면 이 세 가지가 동시에 해소된다. 순서 오류는 컴파일 타임에 잡히고, 검증은 생성자에 모이며, 타입이 곧 의미가 된다. 다만 Value Object가 잡는 것은 타입이 다른 인자끼리의 바꿔 넣기까지다. `transfer(AccountId from, AccountId to, Money amount)`처럼 같은 타입 둘이 나란히 서면 순서를 바꿔도 그대로 컴파일된다. 이 경우는 출금 계좌와 입금 계좌를 묶은 파라미터 객체를 두거나, 빌더로 이름을 붙여 넘기는 식으로 따로 막아야 한다.

반대 극단은 모든 프리미티브 타입을 전용 클래스로 감싸는 **과도한 감싸기** 다. Value Object가 좋다는 것을 알게 된 뒤 생기기 쉬운 습관이다.

```java
// 과도한 예시
class CustomerPostalCode { ... }
class ShippingPostalCode { ... }
class BillingPostalCode { ... }
```

실제로는 `PostalCode` 하나로 충분할 수 있다. 개념적으로 다른 우편번호인지, 아니면 단순히 사용 위치만 다른 같은 우편번호인지를 먼저 판단해야 한다.

크기에 대한 오해도 흔하다. "Value Object는 작아야 한다"고 생각하기 쉽지만, 앞서 본 대로 여러 필드를 가진 큰 구조라도 개념적 정체성이 필요 없고 참조를 공유할 이유가 없다면 Value Object로 모델링하는 것이 맞다.

도메인이 복잡해지면서 결과적으로 많은 멤버가 Value Object가 되는 것은 자연스럽지만, 처음부터 그것을 목표로 삼지는 않는다. 감싸는 기준은 그 값이 자체적인 검증, 연산, 또는 의미 구분을 필요로 하는 도메인 개념인가이지, 경계 안을 지나는 모든 값인가가 아니다. YAGNI(You Aren't Gonna Need It)를 따르자면 그 필요가 코드에 나타났을 때 감싸면 되는데, 내 경우 세 가지를 신호로 삼는다. 같은 검증이 두 번째 자리에 나타날 때, 같은 프리미티브 타입의 인자가 한 시그니처에 나란히 설 때, 그리고 `Money.add()`처럼 그 값에만 성립하는 연산이 생길 때다. 셋 중 하나가 보이면 Value Object를 꺼내고, 그 전까지는 프리미티브로 둔다.

## 경계에서 파싱하기

Value Object는 도메인 내부에서 흐르는 타입이다. 그런데 외부에서 들어오는 데이터(HTTP 요청, DB 조회 결과, 외부 API 응답)는 `String`, `int`, `Map` 같은 프리미티브 타입으로 도착한다. 이것을 도메인 타입으로 변환하는 자리가 경계다. Ports and Adapters(육각형 아키텍처)의 용어로는 어댑터이고, 구체적으로는 컨트롤러, 메시지 수신부, 리포지토리 구현체가 그 자리다.

```java
// 컨트롤러(경계): 외부 표현을 도메인 타입으로 변환
class UserController {
    void createUser(CreateUserRequest request) {
        Email email = Email.of(request.getEmail());
        Age age = Age.of(request.getAge());
        PostalCode postalCode = PostalCode.of(request.getPostalCode());

        userService.createUser(email, age, postalCode);
    }
}

// 애플리케이션 서비스: 프리미티브 타입을 전혀 다루지 않음
class UserService {
    void createUser(Email email, Age age, PostalCode postalCode) {
        // 이미 유효한 타입만 받으므로 재검증 불필요
    }
}
```

경계의 역할은 외부의 언어를 도메인의 언어로 번역하는 것이다. 잘못된 값은 경계를 통과하는 순간 Smart Constructor가 거부한다. 경계 바깥에서는 `String email`이 흐르고, 경계 안쪽에서는 `Email email`만 흐른다. 검증이 사라지는 것은 아니다. 검증은 각 Value Object의 생성자 한 곳에 모이고, 경계 안쪽의 코드는 그것을 반복하지 않는다. 도메인의 불변식을 타입에 표현하면 그 타입을 쓰는 코드 전체에서 불변식이 유지되기 때문이다.

거부하는 방식은 입력의 성격에 따라 달라야 한다. 지금까지의 예시는 모두 `IllegalArgumentException`을 던졌다. 도메인 안쪽 코드가 잘못된 값을 넘기는 것은 프로그래머 오류이므로 예외가 맞다. 하지만 사용자가 입력 폼에 적은 값이 틀린 것은 예상된 상황이고, 이때 예외는 첫 번째 오류에서 멈추므로 이메일과 우편번호가 둘 다 틀렸다는 사실을 한 번에 알려 주지 못한다. 내가 쓰는 방식은 Value Object에 진입점을 둘 두는 것이다. `tryParse`는 `Optional`이나 성공과 실패를 담는 결과 타입을 돌려주고, `of`는 그 위에서 예외를 던진다.

```java
// Email 클래스 안
public static Optional<Email> tryParse(String raw) {
    return raw.contains("@") ? Optional.of(new Email(raw)) : Optional.empty();
}

public static Email of(String raw) {
    return tryParse(raw).orElseThrow(() -> new IllegalArgumentException("올바르지 않은 이메일 형식입니다."));
}
```

컨트롤러는 `tryParse`로 필드마다 결과를 모아 한 번에 응답하고, 도메인 안쪽은 `of`를 쓴다. 검증 로직은 여전히 한 곳이고, 달라지는 것은 실패를 전달하는 통로뿐이다.

DB 조회 결과도 같은 경계를 지난다. 다만 JPA 같은 ORM은 기본 생성자를 요구하고 `final` 필드를 권하지 않으므로, private 생성자와 `final` 필드로 만든 Value Object와 그대로는 맞지 않는다. 내 경우 Value Object가 작으면 `@Embeddable`로 두고 ORM이 요구하는 protected 기본 생성자만 추가하며, 그렇지 않으면 영속용 클래스를 따로 두고 리포지토리 구현체에서 `of`로 변환한다. 어느 쪽이든 변환은 리포지토리 구현체, 즉 경계에서 끝나고 도메인 안쪽에는 Value Object만 들어온다.

## 정리

Value Object는 "식별할 필요 없이 값 자체로 동일성을 판단하는 객체"다. 핵심은 다음과 같다.

- **불변성**: 생성 후 상태를 변경하지 않고 새 객체로 교체한다.
- **값 동등성**: 보유한 값이 같으면 같은 것으로 본다.
- **도메인 로직의 응집**: 값과 관련된 검증과 로직을 그 값의 타입에 함께 둔다.
- **Smart Constructor**: 검증을 우회한 객체 생성을 구조적으로 차단한다. 필드 사이의 관계도 같은 자리에서 확인한다.
- **자료구조로 막기**: 잘못된 조합을 적을 자리 자체를 타입에서 없앨 수 있으면 검증보다 그쪽을 먼저 택한다.
- **경계에서의 파싱**: 외부 입력을 경계에서 도메인 타입으로 변환해 내부를 보호한다.

엔티티가 시간에 따라 변하는 식별 가능한 사물이라면, Value Object는 특정 순간의 개념을 측정하고 설명하는 값이다. Primitive Obsession을 벗어나는 출발점이 Value Object이고, 그 Value Object를 경계에서 만들어 안쪽으로 흘려보내는 구조가 이를 완성한다. 이 구조에서 도메인 계층은 검증을 반복하지 않고도 항상 유효한 상태를 유지한다.
